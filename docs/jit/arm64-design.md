# The ARM64 (AArch64) JIT backend — design reference

This documents the design of the ARM64 lego-JIT backend
(`src/jit/arm64/`), which uses the x64 backend as its template, with
emphasis on the places where AArch64 *differs* from x64 in ways that
produced real bugs during bring-up. Read this before porting to another
architecture or touching the emitters. For milestone status see
[`arm64.md`](arm64.md); for the bring-up debugging war story see
[`arm64-vmnull-race-report.md`](arm64-vmnull-race-report.md).

## Layout

| File | Role |
|------|------|
| `src/jit/arm64/emit.dasc` | DynASM source for the lego emitters (per-op code generation) |
| `src/jit/arm64/emit.c` | Generated from `emit.dasc` by DynASM (checked in; regenerated by `make`) |
| `src/jit/arm64/tiles.dasc` | Expression-JIT tile emitters (included by emit.dasc) |
| `src/jit/arm64/tile_pattern.tile` | Tile selection patterns for the expression JIT |
| `src/jit/arm64/arch.c/h` | Register enums, bitmaps, AAPCS64 calling convention tables |

## Register conventions

Fixed assignments, established in the prologue:

```
x0-x7   ARG1..  (x0 doubles as RV — see below)
x8      indirect result register — avoid
x9-x15  TMP1..TMP7, caller-saved scratch
x16     FUNCTION (IP0) — call target register for callp/callf
x17     (IP1) — short-lived scratch: large-offset materialization,
        resume-address staging in callp/callf. Dead across any call.
x18     platform register — never touch
x19     TC   (MVMThreadContext*, callee-saved)
x20     CU   (MVMCompUnit*, callee-saved)
x21     WORK (MVMRegister* work array, callee-saved)
v0      RVF / first FP argument
```

`RV == ARG1 == x0`: when an emitter must both consume a call's return
value and set up `tc` as the first argument of a following call, it must
consume RV *before* writing ARG1 (x64 has RAX vs RDI and doesn't care).
The same discipline applies to operand loads vs result stores when spesh
aliases a result register with an operand register — read all operands
from WORK before storing the result (see the `sp_add_I` slow path).

`x21` (WORK) is loaded once in the prologue. This is safe for the same
reason it is on x64: `->work` points into the callstack region, which
does not move even when the `MVMFrame` header is promoted to the heap.

## Stack frame

The prologue allocates a fixed 160-byte frame:

```
[sp+  0]  saved x29, x30
[sp+ 16]  saved x19, x20
[sp+ 32]  saved x21
[sp+ 40]  jit_return_address slot (see below)
[sp+ 48+] per-emitter scratch: spills, and the MVMArgs
          {callsite, source, map} block built by the
          runbytecode/dispatch emitters at [sp+48..71]
```

JIT code is re-entered through the prologue on every resume: the runloop
calls `func_ptr(tc, cu, label)` and the prologue ends with `br ARG3` to
the continuation label. All sp-relative slots are therefore
re-established on every entry.

## The `jit_return_address` protocol (`callp` / `callf`)

This is the single most important x64/ARM64 difference in the backend.

MoarVM needs to know "where inside its JIT code is frame X right now" to
resolve **active inlines** (spesh frame walker: dynamic lexical lookup,
exception handler search) and to implement **deopt of a frame that is
currently in a call** — deopt *rewrites the stored return address* so
the JIT code resumes at a deopt/exit label instead of where it left off.
`tc->jit_return_address` points at the slot holding that position.

On x64 this is nearly free: `CALL` pushes the return address at a known
stack depth and the runtime reads/writes it there. **AArch64 `BLR` only
sets LR** — nothing lands in memory. So every call out of JIT code must
maintain the `[sp,#40]` slot by hand. Two macros do this:

```
callp <funcptr>   target known at JIT-compile time (loaded from .data)
callf             target already loaded into FUNCTION (x16)
```

Both expand to:

```
  adr  x17, >9          ; resume address
  str  x17, [sp, #40]   ; publish it as the current position
  blr  FUNCTION
  ldr  x17, [sp, #40]   ; RELOAD — deopt may have rewritten the slot
  br   x17
9:
```

The reload-and-branch is not optional: it is the mechanism by which a
deopt triggered *inside* the callee redirects the JIT frame. A bare
`blr FUNCTION` breaks two ways: frame walkers see a stale position
(wrong active-inline set → wrong handler/dynlex resolution — this
manifests as inline-dependent data corruption, not a crash), and deopt
redirects are silently lost. Every call site must use `callp`/`callf`.

Known, deliberate exceptions (each matching an equivalent x64
limitation): calls made while `sp` is temporarily adjusted for stack
arguments (9+-argument C calls; native calls with stack args).

The dispatch/runbytecode/runcfunc emitters inline the same pattern; the
label after their call doubles as the frame's re-entry point, and the
deopt label registered after the instruction must land exactly there
(do not emit anything between the pattern's `9:` and the end of those
emit functions).

The epilogue (`->exit`) clears `tc->jit_return_address` and returns via
the original LR saved at `[sp,#8]` — never via `[sp,#40]`, so a
trampoline overwrite cannot loop.

## AArch64 encoding gotchas (each caused a real bug)

1. **Scaled load/store immediates are narrow.** `ldr x, [base, #imm]`
   maxes out at 32760 (8-byte access), 16380 (4-byte, e.g. `ldr w…`),
   8190 (2-byte); `add`/`sub` immediates at 4095. Rakudo-scale frames
   and compunits exceed these routinely: work-register offsets,
   spesh-slot/string/coderef indices, lexical env slots. Use the helpers
   `arm64_lea_work`, `arm64_add_off`, `arm64_ldr_off`, `arm64_str_off`
   (or the movz/movk-via-x17 pattern in the `get_string` /
   `get_spesh_slot` macros) for any offset derived from an unbounded
   index.

2. **CMP immediates cannot be negative.** `cmp reg, #-1` is
   unencodable. `MP_LT` and `MVM_BIGINT_32_FLAG` are both -1: use
   `cmn reg, #1`.

3. **Loads don't set flags.** Any `cset`/`csel`/`cneg`/`b.<cond>` must
   be preceded by an instruction that actually sets NZCV
   (`cmp/cmn/tst/fcmp/adds/subs/…`). The x64 template's `test reg, reg`
   has no implicit ARM64 analogue — a ported sequence that drops it
   reads *stale flags from unrelated earlier code*, which is
   deterministic for a given code layout and therefore looks maddeningly
   like a concurrency bug.

4. **DynASM range checking is opt-in.** `DASM_CHECKS` is defined in
   `src/jit/internal.h`. Without it, out-of-range immediates are
   silently truncated into wrong-but-valid instructions. With it,
   `dasm_link`/`dasm_encode` return `DASM_S_RANGE_*` and the frame
   safely falls back to spesh bytecode. Run with `MVM_JIT_DEBUG=1` to
   see which frame failed and at which actionlist offset (the low bits
   of the error code; grep that offset against the `dasm_put(Dst, N`
   calls in the generated `emit.c` to find the emitter).

5. **Typed-pointer derefs can silently emit nothing.** The DynASM form
   `FRAME:reg->env` emitted no instruction at all at four sites (see
   the NB comments in the getlex/bindlex emitters); those use explicit
   `offsetof` instead. If an emitter misbehaves with no visible cause,
   diff the generated `emit.c` against the `.dasc` around that line.

6. **Weak memory order is real here.** Refcounts and any
   publish/consume pattern need explicit ordering that x86-TSO forgave:
   e.g. `MVMJitCode.ref_cnt` decrements are `memory_order_release` with
   an acquire fence before teardown.

## Debugging aids

- `MVM_JIT_DEBUG=1` — JIT diagnostics, including DynASM range failures
  with frame names.
- `MVM_JIT_SKIP_FRAME=substr` — skip JIT for frames whose name contains
  the substring.
- `MVM_JIT_BISECT=K:lo-hi` / `MVM_JIT_ONLY=K:lo-hi` — skip / keep-only
  frames whose FNV-1a(name+cuuid) mod K falls in [lo,hi]. Stable across
  runs regardless of spesh-worker timing (which `MVM_SPESH_LIMIT` is
  not), so a failure can be binary-searched down to a single-frame
  reproducer unattended. `MVM_JIT_BISECT_VERBOSE=1` prints the frames.
- Bail census: run with `MVM_SPESH_LOG=file` and grep
  `"JIT: bailed completely"` to rank unimplemented ops by frequency.

The proven debugging loop for "JIT-only, timing-sensitive" failures:
binary-search `MVM_JIT_ONLY` buckets to one frame → capture its spesh
graph (`MVM_SPESH_LOG`) → histogram its ops → audit those emitters
against x64 → differential runs (`MVM_SPESH_INLINE_DISABLE`,
`MVM_JIT_EXPR_DISABLE`) to split the remaining space. Beware that
timing perturbations (BLOCKING/NODELAY/TSan/heavy logging) change
*which* frames get specialized, and can mask deterministic miscompiles
entirely — a bug that "goes away" under them is not thereby proven to
be a race.
